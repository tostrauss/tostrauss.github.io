Gastropoly — the platform that runs a restaurant's day

Independent restaurants run on paper, spreadsheets and WhatsApp: the roster is on the wall, the delivery notes are in a drawer, the fridge temperatures are on a clipboard and the accountant gets a shoebox. Gastropoly replaces all of it with one multi-tenant app — in daily use at our pilot venue in Austria, where it runs the actual shift.

What I built

  • Shift planning & time clock — rostering plus an offline PIN kiosk that keeps working when the venue Wi-Fi drops.
  • Inventory & supplier ordering — stock levels, order proposals and delivery reconciliation.
  • HACCP compliance — food-safety records that hold up to an inspection, logged where the work happens.
  • Accountant cockpit — DATEV export the accountant actually accepts, no manual re-keying.
  • Reporting — revenue, labour cost and consumption per day, service and product.
  • AI assistant — a Claude-powered assistant with a voice mode for hands-busy staff.

Role

Co-founder. I own the architecture and the product, and I set the engineering process for a three-person team: one slice per branch, mandatory PR review, coordinated migration numbering so 155 migrations never collided.

Architecture

The parts that were actually hard

Tenant isolation in the database

Every tenant row is guarded by Postgres Row Level Security, not by an if in a controller. A forgotten WHERE tenant_id = … returns nothing instead of someone else's payroll.

A venue whose Wi-Fi drops

The kiosk and the PWA are offline-first with a sync queue: staff clock in, log a fridge temperature or take an order with no connection, and the writes reconcile in order once the network returns.

Forecasting a demand curve

Open-Meteo forecasts, AXESS turnstile counts and POS history feed one demand model that drives both the purchase suggestions and the shift plan — the two decisions that cost a restaurant money when they are wrong.

Exports an accountant accepts

DATEV export, PDF and Excel reporting built to the format the tax advisor already works in. The measure of success was zero manual re-keying at month end.

155 migrations, three engineers

One slice per branch, mandatory review and coordinated migration numbering. 370+ automated test files gate every merge, so a schema change can't quietly break another module.

Billing that matches the business

Stripe subscriptions for modular packages — a venue that only needs rostering and HACCP pays for rostering and HACCP.

The hardest requirement was not technical: a seasonal worker has to clock in correctly on the first try, without being trained.

JAMIE — finding people to actually do things with

Bouldering, concerts, Feierabend drinks: JAMIE is a social app for the plans that never happen because nobody organises them. Groups, clubs, a map of activities and real-time chat — live on the App Store and Google Play across six European markets, localised in five languages, with 1,200+ registered users.

What I built

  • Zero to both stores — one React/Vite PWA shipped to the web, to Android as a Trusted Web Activity and to iOS via Capacitor, so a single deploy updates web and Android together.
  • Real-time layer — Socket.IO chat with voice messages, photos, replies, read receipts and reactions.
  • Push pipeline — Web Push and APNs, so a reply reaches you whether you installed from a store or from the browser.
  • Trust & safety — moderation and reporting flows, rate limiting on the endpoints that invite abuse.
  • GDPR, properly — self-service data export and account deletion, not a support-ticket promise.
  • Backups I have restored — encrypted off-site backups with a rehearsed restore, because an untested backup is a rumour.

Role

Co-founder and lead developer. I own the whole technical side: architecture, the store releases, the backend, the real-time stack and the operational work behind six markets.

Architecture

The parts that were actually hard

Three targets, one deploy

Shipping the same PWA as a Trusted Web Activity and a Capacitor app means asset links, store review and native permissions all have to agree with the web build — and a web deploy must never break the installed apps.

Chat that feels instant

Voice messages, photos, replies, read receipts and reactions over Socket.IO, with unread state that survives reconnects and a sleeping phone.

Push across two worlds

Web Push for browser and Android installs, APNs for iOS — one notification pipeline with two very different delivery contracts behind it.

The unglamorous half

Moderation, reporting and rate limiting decide whether a social product survives its first bad actor. They were in the first release, not the backlog.

Six markets, five languages

Localisation, store listings and market-specific content for AT, DE, CH, IT, FR and ES — from one codebase and a very small team.

Data rights by default

GDPR export and deletion built into the product, so a user request is a button press rather than a database session.
